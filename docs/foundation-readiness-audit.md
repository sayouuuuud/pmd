# تدقيق أساس Personal Command Center

**التاريخ:** 2026-08-17  
**نقطة البداية:** `b74f645 refactor: standardize public page controls`  
**النطاق:** تدقيق الأساس قبل دمج مساحة العمل، العملاء، بوابة العميل، التعاون متعدد المستخدمين، الفوترة التجريبية، 2FA التجريبي، ومراقبة Windows.

## النتيجة التنفيذية

المشروع في حالة مستقرة من ناحية واجهة الاستخدام الأساسية: مسارات الأقسام الحالية موجودة، نظام التصميم المشترك مطبق، fallback المحلي يعمل، والبحث الساكن عن عناصر `button/input/select/textarea` الخام خارج `components/ui` لم يعثر على نتائج.

الفجوة الرئيسية ليست في صفحات الحياة اليومية، بل في **نموذج الملكية**. النظام الحالي مبني على مستخدم واحد؛ كل جداول المجال تقريبًا تحتوي `user_id`، وكل المزامنة الحالية تتعامل مع namespace واحد للمستخدم. لا توجد حتى الآن كيانات Workspace أو Members أو Roles أو Clients أو Invitations أو Activity Audit Log. لذلك لا يصح إضافة بوابة عميل أو مشاركة مشروع فوق العقد الحالي مباشرة؛ يجب إدخال طبقة ملكية قابلة للتوسع أولًا.

## ما هو مثبت حاليًا

| المجال | الحالة الحالية |
|---|---|
| واجهة RTL وCairo ونظام الألوان الدلالي | مثبتة ومستخدمة في الصفحات الحالية |
| المكونات المشتركة | Button/Input/Select/Textarea/Dialog/Card/Badge/Empty/Loading موجودة ومستخدمة |
| الأقسام اليومية | Dashboard، Tasks، Notes، Board، Religious، Habits، Journal، Projects، Goals، Finance، Entertainment، Review، Archive، Reminders موجودة |
| fallback المحلي | الحالة الموحدة في `lib/command-center-store.tsx` تحفظ وتستعيد من localStorage ثم تحاول remote hydration |
| Backend الحالي | Route Handlers محمية بجلسة المستخدم في نطاقات متعددة، مع عزل `user_id` في النطاق الحالي |
| المصادقة | Better Auth بإيميل وكلمة مرور؛ لا يوجد 2FA حتى الآن |
| الحالة الإنتاجية | اتصال Neon وcredentials الفعلية وجلسة اختبار حقيقية ما زالت تحتاج تفعيلًا واختبارًا |
| تدقيق عناصر التحكم | لا توجد عناصر تحكم HTML خام خارج `components/ui` في `app` و`components` وفق الفحص الحالي |

## الفجوات البنيوية المؤكدة

### 1. طبقة Workspace والعضوية

العقد الحالي يربط كل سجل مباشرة بالمستخدم. المطلوب إضافة Workspace باعتباره مالكًا منطقيًا للبيانات، مع إبقاء `created_by` أو `owner_id` للتدقيق والإسناد. العضوية يجب أن تكون منفصلة عن المستخدم حتى يمكن لاحقًا دعوة عضو داخلي أو عميل بصلاحية محدودة.

الحد الأدنى المقترح: `workspace`, `workspace_member`, `workspace_invitation`, و`workspace_role` أو قيمة role مضبوطة بعقد واضح. في النسخة الأولى يكون لكل مستخدم Workspace شخصي تلقائي، مع إمكانية إنشاء Workspace عمل لاحقًا.

### 2. العملاء

لا يوجد جدول Client حاليًا. يحتاج العميل إلى ملف مستقل عن المستخدم، مع حقول اتصال وملاحظات وروابط، وحالة، وربط اختياري بملفات ومشاريع وفواتير. بيانات الدخول التجريبية يجب أن تكون كيانًا منفصلًا قابلًا لإخفائه وإيقافه، لا حقولًا مبعثرة داخل العميل.

### 3. مشاركة المشاريع وبوابة العميل

المشروع الحالي مرتبط بـ`user_id` فقط. مشاركة مشروع تحتاج جدول صلاحيات أو علاقة `project_member` تحدد المستخدم أو دعوة العميل، ونطاق الوصول: قراءة، تعليق، تحديث حالة، أو إدارة. بوابة العميل في النسخة التجريبية يجب أن تكون محدودة بمشاريع تمت مشاركتها صراحة، لا وصولًا عامًا لكل مساحة العمل.

### 4. تحديثات المشاريع والتسعير

المشروع الحالي يملك العنوان والوصف والحالة والتقدم والموعد، لكنه لا يملك سجل تحديثات أو ميزانية أو حالات تحصيل. نحتاج كيانات منفصلة لتحديثات المشروع وتسعيراته/دفعاته، مع ربط اختياري بمدخل مالي بعد تأكيد المستخدم أو منطق تجريبي صريح.

### 5. التقويم الموحد

لا يوجد جدول Calendar Event موحد في المخطط الحالي. خطة اليوم والتذكيرات تحمل تواريخ ومصادر لكنها ليست عقد تقويم عامًا. يلزم عقد حدث موحد يملك المصدر والنوع والوقت والمنطقة الزمنية والحالة وروابط المجال، مع إبقاء الأحداث المشتقة قابلة لإعادة البناء وعدم تكرارها بلا ضابط.

### 6. المكتبة والمرفقات

لا يوجد نطاق Library عام في المخطط الحالي. نحتاج Resource وAttachment وربطًا اختياريًا بالعميل والمشروع، مع دعم رابط وملف وPrompt وقالب ومرجع. التخزين الفعلي للملفات يجب أن يمر بمسار تخزين واضح؛ لا ينبغي وضع ملفات كبيرة داخل JSON أو localStorage.

### 7. نشاط Windows

لا يوجد Agent سطح مكتب أو عقد Activity Session. هذا نطاق مستقل يحتاج جامعًا تجريبيًا، طابور مزامنة، إعدادات تشغيل وإيقاف، وتصنيفًا للتطبيقات والنوافذ. سيبدأ كنموذج تجريبي قابل للإيقاف والتشغيل، ثم تأتي التقوية والخصوصية التشغيلية قبل الاستخدام الحقيقي.

### 8. 2FA

Better Auth الحالي لا يحتوي 2FA. سيتم إدخال 2FA تجريبي على مستوى الحساب بعد تثبيت عقد المستخدم والجلسة، مع حالات setup/challenge/recovery في الواجهة والـAPI. سيبقى مفتاح التشغيل التجريبي منفصلًا عن تفعيل Production النهائي.

## عقد الملكية المقترح

1. كل Workspace له مالك ومجموعة أعضاء.
2. كل سجل جديد في النطاقات القابلة للمشاركة يملك `workspace_id`، ويحتفظ بـ`created_by` عند الحاجة.
3. بيانات الحياة الشخصية القديمة تُرحّل إلى Workspace شخصي تلقائيًا، دون كسر localStorage fallback.
4. الوصول إلى أي سجل مشترك يمر عبر membership أو project share، وليس عبر `user_id` وحده.
5. بيانات العميل الخاصة لا تظهر في البحث أو التقويم أو المزامنة إلا إذا كان المستخدم عضوًا مخولًا في Workspace والسجل.
6. الاستدعاءات الحالية أحادية المستخدم تستمر مؤقتًا عبر adapter يختار workspace الشخصي الافتراضي، ثم تُوسّع تدريجيًا.

## ترتيب التنفيذ بعد التدقيق

1. تثبيت عقود Workspace وMember وClient وProject Share والـmigration اليدوية الآمنة دون تشغيل `drizzle-kit generate`.
2. إضافة workspace context إلى الجلسة والـbackend adapter مع إبقاء fallback المحلي متوافقًا.
3. بناء مساحة العمل وملفات العملاء.
4. إضافة تحديثات المشاريع والتسعير والربط المالي التجريبي.
5. إضافة بوابة العميل والمشاركة متعددة المستخدمين.
6. إضافة التقويم الموحد والمكتبة.
7. إضافة 2FA التجريبي ثم جامع Windows التجريبي.
8. إجراء التقوية النهائية: الصلاحيات الدقيقة، تشفير الأسرار، تدقيق النشاط، وإيقاف السلوكيات الحساسة افتراضيًا قبل الإطلاق الحقيقي.

## تنفيذ vertical slice الأول — عقود الملكية ومساحة العمل

تمت إضافة عقد مرحلي يدوي ومراجَع في `server/db/migrations/0010_workspace_work_system_experimental.sql` دون تشغيل `drizzle-kit generate` ودون تعديل journal المختلف. يشمل العقد Workspace وWorkspace Member وInvitation وClient وبيانات الدخول التجريبية وProject Share وProject Update وProject Pricing وCalendar Event وLibrary Resource وActivity Session وSecond Factor Setting، مع إضافة `workspace_id` اختياريًا إلى Project للحفاظ على التوافق مع السجلات القديمة.

أضيفت طبقة وصول في `server/workspaces/access.ts` تنشئ Workspace شخصية عند الحاجة، وتضمن عضوية المستخدم، وتتحقق من العضوية النشطة قبل الوصول لمساحة محددة. كما أضيفت Route Handlers لـ`/api/workspaces` و`/api/clients` مع اشتقاق المستخدم من الجلسة وعدم قبول الملكية من body العميل.

أضيفت صفحة `/workspace` ومكوّنها العربي المتوافق مع RTL وDesign System، وتدعم عرض المساحات والعملاء وإنشاءهما عبر الـAPI أو localStorage fallback عند غياب قاعدة البيانات. أضيف رابط مساحة العمل إلى `TopNav`.

### تحقق الدفعة

- TypeScript: ناجح بعد المخطط والـAPI والواجهة.
- migration: تمت مراجعته يدويًا فقط؛ لم يتم تشغيله لغياب اعتماد قاعدة بيانات فعلي ولوجود اختلاف journal معروف.
- لا توجد secrets أو credentials فعلية في الملفات؛ بيانات الدخول والـ2FA والنشاط موسومة تجريبية حتى مرحلة التقوية.
- ما زال مطلوبًا في الإغلاق التالي: ESLint، `git diff --check`، `next build`، وفحص متصفحي لـ`/workspace` مع fallback المحلي، ثم تحديث الخطة والـcommit/push.

### الفحص المتصفحي الأول

تم فتح `http://localhost:3004/workspace` على localhost:3004. ظهرت صفحة مساحة العمل RTL بنفس PageShell وTopNav الحاليين، وظهر رابط «مساحة العمل» في التنقل. عند غياب backend/session تحولت الصفحة إلى localStorage fallback برسالة واضحة، ثم نجح إنشاء مساحة عمل تجريبية باسم «مساحة اختبار مؤقتة» وتحديث المساحة النشطة بصريًا. عناصر النموذج تستخدم Button/Input/Select/Textarea المشتركة، ولم يظهر عنصر خام في مكوّن Workspace حسب قائمة العناصر المرئية.

أثناء اختبار حفظ العميل، انقطع خادم التطوير وظهرت `ERR_CONNECTION_REFUSED` عند الضغط، ثم أظهر سجل Next أن العملية انتهت بـ exit code 143 بعد نجاح تحميل Workspace وطلبات API غير الموثقة (`401`) وغياب جلسة حقيقية (`503` من auth session). أُعيد تشغيل الخادم باستخدام عملية مستقلة عن جلسة الطرفية لاستكمال اختبار العميل. لا يوجد دليل حتى الآن على خطأ في handler نفسه؛ يجب إعادة الاختبار بعد استقرار الخادم.

أُعيد الاختبار بعد تشغيل خادم التطوير بطريقة مستقلة. عادت Workspace بنجاح، واستعاد fallback المحلي «مساحة اختبار مؤقتة» من localStorage بعد إعادة فتح الصفحة. ظهرت الحالة «وضع محلي مؤقت» ورسالة عدم توفر قاعدة البيانات، كما ظهر العميل التجريبي غير محفوظ بعد في المساحة الشخصية لأن المساحة النشطة عادت إلى المساحة الشخصية عند إعادة التحميل. هذا يؤكد استمرار fallback بين عمليات التحميل ويحدد ضرورة اختيار مساحة الاختبار قبل إضافة العميل.

بعد استقرار الخادم، تم اختيار «مساحة اختبار مؤقتة» بنجاح، وظهر عنوان قسم العملاء مطابقًا للمساحة النشطة. أُدخلت بيانات عميل اختبار غير حقيقية (`test-client@example.invalid`) مع ملاحظة محلية، وجميع الحقول المشتركة ظهرت كما هو متوقع قبل اختبار زر الإضافة.

نجح إنشاء العميل في fallback المحلي؛ ظهر «عميل اختبار مؤقت» وبيانات الشركة والبريد تحت «مساحة اختبار مؤقتة»، مع رسالة «تم حفظ العميل محليًا». فحص localStorage أكد أن `clientsByWorkspace` يحتوي العميل فقط تحت معرّف مساحة الاختبار، بينما قائمة `local-personal` بقيت فارغة. هذا يثبت العزل المحلي الأساسي بين المساحات.

اختبار العزل اكتمل: عند الانتقال إلى المساحة الشخصية ظهر «لا يوجد عملاء في هذه المساحة بعد»، رغم وجود العميل في مساحة الاختبار. بعد ذلك أزيلت مساحة الاختبار وعميلها فقط من localStorage، وبقيت «مساحتي الشخصية» وسجلها الفارغ. لم تُستخدم بيانات حقيقية.

بوابات الجودة النهائية للدفعة: نجح `tsc --noEmit`، و`eslint . --no-warn-ignored`، و`git diff --check`، و`next build`. البناء أنتج 26 صفحة/مسارًا دون أخطاء، مع تحذير Next.js المعلوماتي المعتاد بشأن convention الخاص بـ`middleware` إلى `proxy`. route الجديدة `/workspace` وواجهتا `/api/workspaces` و`/api/clients` ظهرت في مخرجات البناء.

اختبار المتصفح اكتمل على `http://localhost:3004/workspace`: فحص DOM أكد استخدام Button/Input/Select/Textarea المشتركة، إنشاء مساحة عمل تجريبية، إنشاء عميل تجريبي داخلها، عزل العميل عن المساحة الشخصية، ثم تنظيف بيانات الاختبار من localStorage. عند غياب credentials عمل fallback المحلي مع رسالة عربية واضحة، ولم تُستخدم بيانات حقيقية.
